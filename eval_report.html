Critical

CriticalSession cookie never sets Secure, so the auth token leaks over plaintext HTTP

internal/auth/auth.go:45-52 (SetSession), :55-62 (ClearSession)

The HTTP server (server.go) serves plain HTTP with no TLS and no redirect-to-HTTPS. The session cookie is set with HttpOnly and SameSite=Strict but never Secure. Any network observer (open Wi-Fi, upstream proxy, misconfigured reverse proxy dropping to HTTP) captures the admin session token in cleartext and replays it for the full 24h window. There is no config flag to force it either.

http.SetCookie(w, &http.Cookie{
    Name:     cookieName,
    Value:    value,
    Path:     "/",
    HttpOnly: true,
    MaxAge:   int(sessionMaxAge.Seconds()),
    SameSite: http.SameSiteStrictMode,   // Secure: MISSING
})

Fix: add Secure: !cfg.Dev (or an explicit config toggle). ClearSession should mirror the same attributes so intermediaries don't reject the clear.

CriticalStateless session tokens cannot be revoked, so "logout" is cosmetic

internal/auth/auth.go:55-63 (ClearSession), :89-112 (verify)

The session token is a self-contained HMAC over only an issuedAt timestamp. There is no server-side session store, no nonce, no revocation list, no password-change invalidation. ClearSession only deletes the client's cookie. If a token is ever captured (see the Secure finding above), logging out does nothing. The stolen token stays valid for the full 24 hours regardless. Rotating the admin password also does not invalidate live sessions, because the token isn't bound to the password hash.

payload := base64(fmt.Sprintf("%d", issuedAt))   // only the timestamp
value  := payload + "." + sm.sign(payload)        // any valid HMAC = admin

Fix: bind the token to a server-side secret that rotates on logout/password-change, or include a hash of the current password in the signed payload so a password change kills all sessions. At minimum add a random nonce persisted server-side.

High

HighNo HTTP server timeouts, allowing trivial Slowloris DoS

internal/server/server.go:54-57

The http.Server is constructed with only Addr and Handler. ReadTimeout, ReadHeaderTimeout, WriteTimeout, and IdleTimeout are all zero (unlimited). A handful of slow clients holding connections open indefinitely will exhaust the server. This is worse here than usual because SQLite runs with SetMaxOpenConns(1), so a single stuck request holding the DB serializes everything.

return &http.Server{
    Addr:    fmt.Sprintf(":%d", cfg.Port),
    Handler: r,
}, nil   // no timeouts at all

Fix: set ReadHeaderTimeout: 10*time.Second, ReadTimeout, WriteTimeout, IdleTimeout.

HighNo security response headers anywhere

internal/handlers/handler.go:122-140 (render), internal/server/server.go:21-23

No middleware or handler sets Content-Security-Policy, X-Content-Type-Options: nosniff, X-Frame-Options/frame-ancestors, or Referrer-Policy. The admin editor and blog render user/markdown-derived content. Without a CSP, any XSS that slips past goldmark's escaping (or a future template that trusts input) is unmitigated, and the admin panel is clickjackable.

Fix: add a security-headers middleware. At least nosniff, frame-ancestors 'none', and a restrictive default-src 'self' CSP.

HighNo CSRF protection on admin mutations

internal/handlers/admin.go:17,60,84 & internal/server/server.go:44-52

All admin state changes are POST with no CSRF token: login, create, update, delete, logout. The only defense is the cookie's SameSite=Strict. That is a real mitigation for modern browsers, but it is a single point of failure. It does nothing for older browsers, and any future need to loosen SameSite (e.g. embedding, OAuth callback) instantly reopens CSRF. Notably logout being CSRF-able lets an attacker force-logout the admin, and login CSRF can fixate a session.

Fix: add a per-session CSRF token (hidden form field checked server-side) in addition to SameSite. Defense in depth.

HighNo rate limiting or lockout on admin login

internal/handlers/admin.go:17-27

AdminLoginPost accepts unlimited password attempts. bcrypt slows each guess and covers timing, but there is no per-IP throttle, no lockout, no delay. Combined with a single shared admin password, this is an open online brute-force target. Because bcrypt is CPU-heavy and SQLite is single-connection, a flood of login attempts also doubles as a CPU-exhaustion DoS.

Fix: add rate limiting (e.g. httprate) on /admin/login and a backoff/lockout after N failures.

HighZero test coverage on the handlers and db packages

internal/handlers/*.go, internal/db/db.go (no _test.go files)

go test ./... reports [no test files] for internal/handlers and internal/db. The handlers package holds every piece of business logic that a bug would actually hurt: the publish/unpublish action logic, delete, template rendering, static generation, markdown rendering, DSN parsing, and migration wiring. The server_test.go covers routing at the edges, but the branch logic inside AdminUpdatePost (delete vs publish vs draft), generate.go, and DSN error paths in db.Open are entirely untested. This is exactly where the finding below (#unpublish) hides.

Fix: add handler-level tests for update/delete/publish transitions and a db test for the unsupported-DSN error path.

HighEditing a post silently unpublishes it unless you click "publish"

internal/handlers/admin.go:90-92, 103

AdminUpdatePost sets updated.Published = r.FormValue("action") == "publish". Published state is derived only from which button was pressed, not from the post's existing state. If the editor form has a "Save" button (action != "publish"), or the admin edits a live post and saves without hitting the exact publish action, the post is unpublished and vanishes from the public site. It ignores existing.Published entirely. This is a data-visibility bug waiting to bite in production, and it is untested (see coverage finding).

updated.Published = r.FormValue("action") == "publish"   // ignores existing state
// action=="save" or anything else  =>  Published=false  =>  post disappears

Fix: treat publish/unpublish as explicit distinct actions and default to preserving existing.Published on a plain save.

Medium

MediumN+1 queries when resolving tags on every create/update

internal/models/post.go:188-202 (resolveTags)

resolveTags runs a separate FirstOrCreate per tag name (one round trip each). For a post with M tags, that's M queries before the insert. On SQLite (max 1 conn) each is serialized. Not fatal at a personal-blog scale, but it is a genuine N+1 and it runs inside Update's transaction, lengthening the write lock.

Fix: batch into one SELECT ... WHERE name IN (...) then bulk-insert the missing names.

MediumPostgres join has no index on post_tags.tag_id

internal/db/migrations/postgres/001_initial.sql:17-21, sqlite/001_initial.sql:17-21

post_tags PK is (post_id, tag_id), which indexes post_id first. ListByTag joins tags.id = post_tags.tag_id (the reverse direction) with no standalone index on tag_id. On Postgres this forces a scan on the tag→post lookup as the table grows. SQLite has the same gap. Also there is no index supporting ORDER BY created_at DESC on posts, so List sorts via a scan.

Fix: add CREATE INDEX ON post_tags(tag_id) and CREATE INDEX ON posts(created_at).

MediumrenderMarkdown returns template.HTML, disabling autoescape; safety depends entirely on goldmark config

internal/handlers/blog.go:13-23

The rendered markdown is wrapped in template.HTML, which tells html/template "trust this, do not escape." The only thing preventing stored XSS is that the goldmark instance omits WithUnsafe(), so raw HTML in post bodies is escaped. That's correct today, but it's fragile: a future dev adding WithUnsafe or an HTML-passthrough extension instantly turns the admin-authored body into stored XSS with zero other guardrails (no CSP; see High finding). The safety of the whole app hinges on one missing option with no defense in depth.

Fix: keep goldmark safe, add a sanitizer (bluemonday) as a second layer, and add a CSP.

MediumServer binds all interfaces with no bind-address config

internal/server/server.go:55

Addr: fmt.Sprintf(":%d", cfg.Port) binds 0.0.0.0 unconditionally. There is no way to restrict the admin surface to localhost / a private interface behind a reverse proxy. Combined with no Secure cookie and no rate limiting, a dev who runs this directly on a box exposes the admin panel to the internet by default.

Fix: add a configurable bind_addr (default 127.0.0.1 or document the reverse-proxy expectation).

MediumUpdate partial failure leaves post updated but tags stale, plus Updates(map) won't clear falsey fields correctly if reused

internal/models/post.go:134-151

The transaction is correct in that both statements share tx. But note the update uses a map[string]any specifically to force published:false to persist (GORM struct updates skip zero values). That's a subtle GORM footgun the author navigated (good), but it means any future field added to the struct-update path will silently drop false/0/"" values. Also, tx.Model(&r).Updates(...) on a non-existent ID updates zero rows with no error, so updating a deleted post "succeeds" silently before the tag replace.

Fix: check RowsAffected after the update and return a not-found error if zero.

MediumMigrations create tables but GORM models could drift (no AutoMigrate, no schema assertion)

internal/db/db.go:87-94, internal/models/post.go:24-43

Schema is owned by goose SQL; GORM models carry their own tags (uniqueIndex, not null, default:false, m2m join names) that are never applied or verified because there is no AutoMigrate. The joinForeignKey:post_id/joinReferences:tag_id mapping must match the hand-written post_tags exactly. If someone edits one and not the other, GORM will generate queries against columns that don't exist and fail only at runtime. Nothing tests the postgres migration path at all.

Fix: add a startup schema check, or a CI test that runs both migration sets and exercises the m2m round-trip on Postgres.

MediumListByTag double-loads tags: JOIN filters, Preload re-queries

internal/models/post.go:69-85

The query JOINs post_tags/tags to filter by tag name, then Preload("Tags") issues a second query per result set to hydrate all tags. Functionally fine, but the JOIN can also produce duplicate posts rows if a post matched multiple times (not here since it filters one tag, but it's a fragile pattern: adding a second tag filter would silently duplicate rows without a DISTINCT/Group).

Fix: prefer a subquery (posts.id IN (SELECT post_id FROM post_tags ...)) to keep filtering and hydration cleanly separated.

Low

LowClearSession cookie attributes don't match SetSession

internal/auth/auth.go:55-63

The clearing cookie omits HttpOnly, SameSite, and (once added) Secure. Some proxies/browsers treat a Set-Cookie whose attributes differ from the original as a distinct cookie and won't overwrite it. Mirror the attributes to guarantee deletion.

LowError strings from the DB leaked to the admin UI

internal/handlers/admin.go:67, 106

On create/update failure the raw err.Error() (e.g. GORM/SQLite constraint text) is rendered into the editor template. It's admin-only, so impact is low, but it leaks schema/driver internals and, if the template ever renders it unescaped, could reflect input.

LowSample config duplicated in two places, will drift

main.go:168-184 (const sampleConfig) vs docs/ntx.sample.toml

The embedded sampleConfig and the docs sample are maintained separately. gen-config's ReplaceAll also depends on the exact string session_secret = "" (fixed spacing); reformat the template and the secret silently stops being injected, shipping a config with an empty secret that then fails validation confusingly.

LowAbsurd itoa helper in tests

internal/server/server_test.go:482-485

strings.TrimSpace(strings.ReplaceAll(strings.ReplaceAll(fmt.Sprintf("%d", n)...))) is strconv.FormatInt(n,10) written by someone fighting a phantom. It's dead-weight and signals copy-paste under duress.

LowDev mode reparses templates from disk on every request

internal/handlers/handler.go:34-52, 82-86

In dev, Has does an os.Stat and Get re-ParseFiles per request. Fine for dev, but there is no guard preventing Dev:true in production config, where this becomes a per-request filesystem hit and a way to pick up half-written template files. No config validation forbids dev+prod-like settings.

LowStats() uses three separate COUNT queries

internal/models/post.go:169-185

Three round trips (total, published, tags) rendered on every admin dashboard load. Trivial now, but on SQLite's single connection it's three serialized queries where one SELECT count(*), count(*) FILTER(...) would do. Also int(t) casts from int64 to int (harmless on 64-bit, a latent overflow on 32-bit).

Info

InfoSingle shared admin password: no user model, no MFA

internal/config/config.go:29, internal/auth/auth.go

Auth is one bcrypt hash in the config file. Acceptable for a personal site, but there's no per-user auditability, no MFA, and rotating the password requires editing config and restarting. Worth stating as an accepted design limit.

InfoNo graceful shutdown

main.go:63-64

srv.ListenAndServe() is called with no signal handling / srv.Shutdown. On SIGTERM, in-flight requests and the WAL checkpoint are cut off. Low risk for SQLite WAL but worth adding.

InfoNo request context / cancellation reaches the DB layer

internal/models/post.go (all methods)

Store methods take no context.Context; they use the base *gorm.DB. A client disconnect can't cancel a slow query. Fine at this scale, but the store API forecloses adding timeouts later without a signature change.

InfoStatic file server relies solely on stdlib traversal protection

internal/server/server.go:39

http.FileServer(http.Dir(cfg.StaticPath)) behind StripPrefix is safe against ../ traversal (stdlib cleans paths), and directory listings are a stdlib default. No bug, noted because it's the one place traversal could appear and it's handled correctly.

Infogenerate.go copies static tree with fixed perms, follows no symlinks check

internal/handlers/generate.go:124-157

copyDir walks StaticPath and rewrites everything 0644/dirs 0755, discarding original perms (fine for a web root). It doesn't special-case symlinks: filepath.Walk doesn't follow them, so a symlink in static/ is copied as a regular file of the link target's path bytes only if opened... actually it os.Opens and copies target content. Low concern for a trusted static dir; noted for completeness.

InfoSQLite pinned to a single connection

internal/db/db.go:43

SetMaxOpenConns(1) is the correct, safe choice for SQLite writes and avoids SQLITE_BUSY. Flagged only because it turns every other latency issue in this report (no timeouts, N+1, 3x COUNT, bcrypt on login) into a global serialization point. The mitigations above matter more because of this.

Strengths

GoodThings done right

  • HMAC session verification uses hmac.Equal (constant-time), no timing oracle on the signature. Session expiry is checked. (auth.go:95, 107)
  • Passwords are bcrypt at DefaultCost; comparison via CompareHashAndPassword is constant-time. (auth.go:31-38)
  • Config validation is strict and fail-closed: refuses to start without a ≥32-char session secret and a password hash. (config.go:74-82)
  • All SQL goes through GORM parameterized queries / placeholders, no string-built SQL anywhere; the Sprintf-SQL grep found nothing.
  • goldmark configured safe by default (no WithUnsafe), and there's an explicit XSS regression test asserting <script> is stripped. (server_test.go:448)
  • render buffers to a bytes.Buffer before writing, so a mid-template error yields a clean 500 instead of a half-written 200. (handler.go:132-139)
  • Consistent error handling: gorm.ErrRecordNotFound mapped to nil,nil and turned into 404s; DB errors surfaced as 500 with logging, not swallowed.
  • DB cleanup is correct: defer sqlDB.Close() in both commands, and failure paths in openSQLite/openPostgres close the handle before returning.
  • FK enforcement + WAL enabled for SQLite; ON DELETE CASCADE on post_tags keeps join rows consistent when a post is deleted. (db.go:44-49, migrations)
  • chi middleware includes Recoverer so a handler panic becomes a 500 instead of crashing the process. (server.go:23)
  • Clean layering: public Post type vs internal dbPost, store interface isolates GORM, handlers don't touch the DB directly. Genuinely tidy.
  • go vet clean, tests pass, and auth/config/models are well-covered including tamper, expiry, wrong-secret, and dedup cases.

Bottom line: the crypto and SQL layers are solid: no injection, no timing holes, sensible fail-closed config. The exposure is operational: an unrevocable session token over a cookie that isn't Secure, on a server with no timeouts, no security headers, no rate limiting, and one silent data-visibility bug (edit→unpublish) sitting in the untested handlers package. Fix the two Criticals and the timeout/headers/rate-limit trio before this faces the internet.
